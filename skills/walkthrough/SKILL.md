# Walkthrough

한 번에 한 단계만 설명하고, 사용자의 답을 받기 전에는 다음 단계로 넘어가지 않는다. 사용자가 단계별 설명을 요청했을 때 시작한다.

## 준비

- 직전 대화와 이미 확인한 자료를 먼저 활용한다. 설명할 대상이 없으면 무엇을 설명할지 한 줄로 묻고 기다린다.
- 코드 변경이라면 작업 상태와 실제 기준 브랜치를 확인하고, 관련 diff와 주변 코드, 참조 문서를 읽는다. 커밋되지 않은 변경도 설명 범위에 포함되는지 확인한다. Git이나 파일 접근이 없으면 제공된 자료를 사용한다.
- 자료로 확인한 사실과 추론을 구분하고, 알 수 없는 의도는 지어내지 않는다.

## 순서

보통 3~7단계로 나누되, 작은 주제는 더 적어도 된다. 파일 순서보다 인과관계를 따른다.

문제와 필요성 → 관찰되는 변화 → 동작 흐름과 구현 위치 → 선택 이유와 트레이드오프 → 관련 위험과 확인할 점.

단계 수만 먼저 알리고 첫 단계부터 시작한다. 전체 목차는 사용자가 원할 때 보여준다. 질문이나 이해 수준에 따라 순서와 단계 수를 조정한다.

## 진행

각 응답에는 한 단계와 확인 질문 하나만 담는다.

```text
[2/5] 결제 창이 열리는 흐름

핵심을 3~6문장으로 설명한다.
필요하면 실제 파일 위치나 짧은 코드로 뒷받침한다.

다음으로 넘어갈까요, 더 설명할까요?
```

- 코드 인용은 필요한 부분만 보통 3~5줄로 제한한다. 확인한 파일은 환경에 맞는 링크나 `file:line`으로 가리킨다. 줄 번호를 추측하지 않는다.
- 환경에서 사용할 수 있고 허용된 질문 UI가 있으면 `다음으로` / `더 설명해줘` 선택지를 제공한다. 없으면 일반 채팅으로 묻는다. 특정 도구는 필수가 아니다.
- 질문한 뒤 응답을 마치고 실제 사용자 답을 기다린다. 무응답이나 시간 경과를 동의로 취급하지 않는다.
- `다음으로` 또는 같은 뜻의 답을 받으면 다음 단계를 설명한다.
- `더 설명해줘`라면 같은 말을 반복하지 말고 구체적인 사례, 흐름도, 익숙한 개념과의 비교로 바꾼다. 두 번 설명해도 막히면 어느 부분이 어려운지 묻는다.
- 별도 질문이 오면 답하되 단계를 넘기지 않고 다시 확인한다. 현재 이해에 필요한 질문은 뒤로 미루지 않는다.
- 사용자가 요약, 건너뛰기, 종료 등 다른 진행 방식을 요청하면 따른다.

## 마무리

마지막 단계도 확인을 받은 뒤 전체 흐름을 3~4줄로 정리한다. 헷갈렸던 지점과 미확인 사항이 있으면 짚는다. 사용자가 요청한 경우에만 정리 파일을 만든다.
